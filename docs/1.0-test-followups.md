# 1.0 application test follow-ups

This is a source fix batch while hardware testing continues. It is not a stable
release or a new console package. Keep the working `87c47a5` bootloader disc.

## Confirmed source defects addressed

| Change | Evidence and intended behavior |
| --- | --- |
| Lua coroutine ownership | A host reproduction using the bundled Lua core loses the second live coroutine when the first is released. Independent registry references now survive non-LIFO release, clearing the parent stack and repeated garbage collection. The Lua panic output hook also uses the correct function-pointer declaration. |
| File Manager directory scans | Read the directory before passing its resulting count to the pending scan. C++ argument evaluation order could previously pass zero entries. A host regression verifies the actual scan method. |
| Utility stick input | Settings, File Manager, GD Play, Network, Speedtest, Memtest, BIOS Flasher and Region Changer retain the analog pointer, with native D-pad focus. Controller A produces one action; idle pointer events do not erase the D-pad highlight. MIE JVS auxiliary controllers also map the stick to navigation without changing JVS calibration data. |
| Confirmation choices | D-pad directions select a visibly highlighted Confirm or Cancel; A activates that selection and B cancels. Two-button dialogs start on Cancel. Alerts select their only active button. Editing a prompt still receives spaces and keyboard events. |
| Classic removal | The old Main desktop is excluded from builds, catalogs and startup choices. Incremental packaging removes stale output and rejects Classic content. Old Main startup/home settings resolve to Launch App, and old SD copies are ignored. Historical source and attribution remain. |
| Speedtest diagnosis | A mismatch still fails verification. The first bad byte offset and expected/actual values now appear on screen and in the saved report. Host fault injection checks an 8 MiB run, short transfers and corruption after the first 256 KiB chunk. |

## Still open on hardware

- ISO Loader intermittent exception and VMU Manager invalid-memory-read exception.
  The photographed VMU fault points into heap allocation; this does not identify
  the original invalid write or prove the Lua fix resolves it.
- File Manager reboot during opening. The lifetime and scan defects above are
  fixed, but the reported reboot has not been reproduced on the host.
- Returning from Settings or Network fails to reparse Launch App XML with a NUL
  control character. A common memory or storage cause is still under investigation.
- Speedtest SD read-back mismatch. The host pattern/verification test passes and
  detects injected corruption; the actual console mismatch remains unexplained.

Collect remaining findings before one combined console build. In that retest,
check repeated app open/close cycles, both stick and D-pad controls, dialog
choices, absence of Classic, and Speedtest's saved report. Host checks do not
establish console memory, SD timing or peripheral stability.

## Rip-log findings and the CRC exception

The supplied 31-track rip completed all 518,827 sectors in 1,944.762 seconds.
Its 450 failed bulk-sector checks report EDC-only failures (`flags=4`): 72 on
track 1, eight on track 3, and 370 on track 31. Every failure on tracks 1/3 is
at zero-based slot 11 of a 16-sector buffer; track 31 failures are at slot 12.
The existing individual rereads then succeed. Audio tracks do not receive the
same Mode 1 EDC validation, so their lack of these messages is not proof of
unaffected data.

That fixed position warrants investigating buffer/read handling. It does not
prove disc damage, a cache defect, or insufficient RAM. The uploaded log ends
before verification and contains no register dump for the new CRC exception.

The next test records up to eight bad bulk-sector snapshots per rip and compares
them with the existing successful individual reread: buffer address, slot, CRC,
changed byte count, first/last offsets, and the first differing byte values.
This adds no disc reads and changes neither validation nor retry limits. Keep
`rip.log` from the next test even if the dump completes.

Before either the automatic saved-stream CRC check or a manual saved-dump scan,
GD Ripper now joins its music worker, destroys its stream and frees the cached WAV
and feed buffer. RAM snapshots bracket that operation. Music resumes with the
same track/volume only after verification finishes and the storage gate is
released. Error and cancellation follow the same cleanup; a closed app cannot
restart music. Muted music stays muted. Music still plays from RAM while ripping.
This is a controlled safeguard; music has not been established as the crash cause.

The automatic CRC check now also skips an unused 37,632-byte sector-buffer
allocation. A manual storage scan still needs a read buffer. Neither operation
loads an entire disc image or music playlist into RAM.

## RAM measurements

Core app transitions print snapshots and append `kui-memory.log` to the SD/IDE/PC
installation folder, normally `/sd/DS/kui-memory.log`. This log has a 128 KiB cap;
copy it to the computer, then remove that log before a fresh test if it is full.
A logging failure is nonfatal. The working bootloader disc can load the updated
SD files; retain it.

- `heap_used`: allocated main-heap bytes.
- `heap_free`: reusable bytes inside the existing heap.
- `unclaimed`: space above the heap break, excluding KOS's 64 KiB kernel stack
  and the final four-byte allocation boundary.
- `available`: estimated `heap_free + unclaimed`, not a guarantee that one
  allocation of that size can succeed. PVR memory is separate.
- GD Ripper also samples counters every five seconds and logs the lowest sampled
  availability at phase boundaries. Sampling does no storage I/O. Brief peaks
  between samples can be missed. Invalid/changing snapshots are rejected.

Use a keyboard's F1 console and `mstats` for a manual snapshot; F1 returns to the
app. `opened` can precede asynchronous music loading. `closed` can precede module
unloading; compare the next `before-load` record for the same route when checking
for persistent growth. Utility logs cover transitions, not temporary allocation
peaks while tests are running. Do not use Memtest to exhaust RAM as a measurement.

Only one WAV is cached per visit, approximately 0.73–1.01 MiB plus a 16 KiB feed,
a worker stack and stream overhead. Choosing Music Off alone retains that WAV.
For a cache-free control, select Off, leave the app and reopen it. The five tracks
total approximately 4.46 MiB on storage; they are not loaded together.

If verification still raises an exception with the WAV freed, photograph PC, PR,
FAULT and EVENT and retain the logs. The exception message alone does not show
whether RAM exhaustion or an invalid access caused it.

## Validation

The restored batch passed 185 host tests, with one Linux FAT/exFAT interoperability
class skipped because exfatprogs is unavailable. Host validation covers the actual
counter/sampler/logger, buffer-fault rereads,
automatic and manual verification through the service thread, music shutdown while
the storage gate is held, and simultaneous close/suspend using real threads.
The SH-4 package and hardware retest remain pending. Address/undefined-behavior
instrumentation is enabled where supported; local LeakSanitizer uses
`ASAN_OPTIONS=detect_leaks=0` because process inspection is unavailable.
